# Facts

- A generated inventory discovers every public regular Scraps component family and public runtime and type export from the latest monolith source. It reports new, removed, covered, and explicitly excluded entries instead of assuming the count will remain 48.
- Existing green evidence counts as completed work. The goal starts from the current 48 complete manifest records, 175 runtime exports, 59 type exports, 48 registry items, 48 playground workbenches, 192 Scrapscn snapshots, and 11 local Code Connect mappings. Work is repeated only when the latest-source inventory or a failing check shows drift.
- Every portable public component usage compiles and keeps its observable behavior after only the import path changes. The manifest records the four approved CSS-in-JS-only input exceptions and fails if another exception appears without an explicit scope change.
- In-scope components use Tailwind classes and static CSS where needed. They do not ship Emotion, styled-components, copied CSS-in-JS helpers, or a general Emotion-to-Tailwind converter. Picture-in-Picture may copy the already compiled static stylesheet into the browser-created document because that document does not inherit styles from the opener; it does not generate component styles or inject styles into the main document.
- One clean temporary project installs the base theme and Checkbox from the locally built shadcn registry and renders it successfully. Automated registry checks then enforce the same schema, file closure, dependency closure, and build rules for every other component item without installing 48 separate projects.
- Checkbox is the reference proof for Figma interoperability. Its parserless Code Connect mapping uses the canonical node and property vocabulary, generates Scrapscn JSX that compiles, and uses the distinct Scrapscn React label. Other components with canonical Figma evidence follow the same checked mapping convention. The goal does not publish mappings remotely or build a general source converter.
- The visual system captures a frozen canonical monolith image and a matching Scrapscn image for each review scenario with the same theme, viewport, state, fonts, locale, and reduced-motion setting. The capture records the monolith commit and does not depend on a stale server checkout.
- Each visual pair has an approved, fixed, or documented-deviation result. Contract, behavior, accessibility, missing-content, broken-state, and major layout differences block completion. Small spacing, antialiasing, and rendering differences may pass when the evidence records the difference and reason. No visual pair remains unreviewed.
- The full-screen local playground remains the primary validation and prototyping environment. Every discovered component family has a workbench, URL-restorable controls, light and dark modes, narrow and wide views, and a shareable route. Templates compose the same public components and work in local and Vercel Preview builds.
- A component pass compares the latest contract, fixes only detected API, behavior, or visual differences, runs that component's focused checks, records its result, and moves on. It does not rerun the full repository suite after every component.
- After the last component change, the full unit, parity, type, format, lint, production build, Storybook, playground, template, registry, Code Connect, and visual regression checks run once. A new full run is required only after a later code change.
- The goal is complete when the generated inventory has no unexplained entry, all portable contracts and focused behavior checks pass, all registry and Figma convention checks pass, every canonical visual pair has a result, no blocking visual difference remains, the playground and templates work, and the final full check is green.
